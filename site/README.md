# Сайт «Глоссалия»

Сайт показывает выбранные материалы [Glossolalia Explorer](https://github.com/hayOfLife/glossalia-explorer). Основной адрес — [glossalia-explorer.tuqo.ru](https://glossalia-explorer.tuqo.ru/). Исходная оболочка находится в `site/public_html/`, готовые для Tuqo статические страницы собираются в `site/build/`; записи для календаря находятся в `site/public_html/data/entries.json`.

## Состояние на 29.09.2026

- Разделы: «О глоссалии», «Новости», «Календарь», «Каталог ситуаций», «Как сделать перевод иных языков», «Справка», «Донат», «для ИИ (AI)».
- В «Справке» есть шесть тематических карточек со страницами, включая рассказ автора о себе; раздел о глоссалии отдельно показывает языковые сопоставления и степень их проверки.
- «Каталог ситуаций» содержит таблицу из трёх ссылок на отдельные страницы; подробные материалы для ситуаций 2 и 3 пока готовятся.
- В «Календаре» текущий день выбирается по московскому времени. Можно переключать месяцы и выбирать любую дату.
- В календаре есть шесть исходных карточек `§T00014`, `§T00016`–`§T00020` и разборы `§T00032`–`§T00035`. Исходные строки показаны отдельно от предположений о переводе.
- У карточек указана **дата получения транскрипции**. Она не считается датой аудиозаписи; точное время для этих карточек неизвестно.
- Новости пока не наполнены; раздел «Донат» ведёт на страницу ЮMoney.
- Входа пользователей и публичных форм нет.
- На Tuqo опубликованы «Справка», страницы каталога и кнопки оценки транскрипций. Отправка изменений в GitHub сама по себе не обновляет Tuqo.
- Общие счётчики обслуживает отдельный HTTPS API на VPS. Сайт обращается к `https://94-232-41-163.sslip.io/glossaliae/reactions`; 28.09.2026 ответ API проверен из обычной сети Windows, работа кнопок в браузере посетителя ещё проверяется. Изменения кода голосования пока не отправлены в GitHub.

## Структура

- `public_html/` — единственный каталог, который должен быть доступен посетителям.
- `public_html/data/entries.json` — опубликованный снимок записей для браузера.
- `calendar-index.json` — список уже учтённых файлов транскрипций; новые файлы сравниваются с ним.
- `scripts/update_calendar.py` — генератор календарных карточек из новых Markdown-файлов.
- `database/schema.sql` — схема MySQL 5.7.
- `database/seed.json` — начальные шесть записей, извлечённые из публичных карточек репозитория.
- `database/config.example.php` — образец параметров БД без учётных данных.
- `scripts/import.php` — однократный импорт начальных записей в пустую таблицу.
- `scripts/publish.php` — создание нового снимка из опубликованных записей БД.

## Оценки транскрипций

Tuqo раздаёт только статические файлы. Общие счётчики ведёт отдельный HTTPS API на VPS. Серверный процесс и его файл голосов отделены от публичных файлов сайта. Исходники API пока не отправлены в GitHub; эта страница описывает действующее размещение, а не инструкцию по его воспроизведению из текущего коммита.

Публичный API проверен тестовым голосом со снятием; после проверки счётчик вернулся к исходному значению. Для посетителей голосование появится после отдельной публикации подготовленных статических файлов на Tuqo. Никакие ключи или пароли в браузерный код и Git не добавляются.

Голос привязан к случайному идентификатору в браузере, а не к человеку: очистка хранилища или другой браузер позволяют проголосовать снова. На сервере сохраняется только SHA-256 этого идентификатора и выбор лайк/дизлайк. API ограничивает изменения голосов до 12 за 10 минут для идентификатора и 40 за 10 минут для IP; посетители за одним IP делят общий лимит. IP и счётчики лимитов хранятся только в памяти процесса и сбрасываются при его перезапуске. Эти ограничения замедляют накрутку, но не исключают её полностью.

## Промпт Алисы

Кнопка «Начать>» загружает [компактный промпт](public_html/data/promptForAlice_guessingTheMeaningOfTheGlossary.min.txt) и передаёт его Алисе AI. Ссылка «Скачать файл промпта» ведёт на [полную версию](public_html/data/promptForAlice_guessingTheMeaningOfTheGlossary.txt). После первого ответа Алисы посетитель отправляет ручную транскрипцию отдельно.

## Локальный просмотр

Из корня репозитория в PowerShell при установленном Python запустите `python -B -X utf8 site/scripts/build_static.py`, затем `python -m http.server 8765 --directory site/build` и откройте `http://127.0.0.1:8765/`. Первая команда записывает готовые файлы в `site/build/` и `site/content-manifest.json`, не удаляя другие файлы; вторая показывает готовый сайт локально и не меняет файлы. Прямое открытие `index.html` как файла может заблокировать чтение JSON. Просмотр не проверяет доступность Tuqo либо API голосования.

## Обновление сайта и данные

Tuqo нужно обновлять отдельно от GitHub. Архив для загрузки создавайте из содержимого `site/build/`: в корне должны быть `index.html`, `assets/`, `data/`, `sitemap.xml`, `robots.txt`, `content-manifest.json` и каталоги отдельных страниц. Каталоги `database/`, `scripts/` и серверный PHP-код не загружаются как публичные файлы.

Сборщик создаёт отдельные HTML-адреса для основных разделов и всех опубликованных разборов, указанных в календаре или на страницах сайта. Внешний вид основных разделов берётся из той же оболочки и CSS. Ссылки разделов ведут по обычным путям; старые адреса с `#` не поддерживаются. `sitemap.xml`, `robots.txt`, уникальные заголовки, описания, canonical-адреса и разметка `CreativeWork` для разборов формируются при сборке. Разбор читается прямо из исходного Markdown без изменения файла. Источник транскрипции в карточке указан как «автор», а ссылка на Markdown позволяет сверить опубликованный текст с GitHub.

Для новой карточки храните отдельно исходную транскрипцию и текст для копирования с маленькими корректировками, если он отличается. Сборщик берёт текст для копирования из поля `copyText` в `entries.json`, затем из раздела `## Текст для копирования` исходного Markdown либо из уже существующего блока `textarea` в оболочке сайта. Если отдельный текст не задан, он копирует раздел «Необработанная транскрипция» из исходного Markdown; для старых карточек без такого раздела берёт `bodyText` из календаря. Поле `bodyText` остаётся текстом календарной записи. Дату записывайте одним полем с известной информацией, не придумывая час. Тема, машинный разбор и авторское толкование должны быть различимы в исходном Markdown; отсутствующие сведения не заполняйте догадками. История правок карточки пока не ведётся.

Для новых материалов используйте такой порядок смысловых полей. Это шаблон для последующего наполнения, а не требование переписать уже присланные автором файлы:

| Поле | Содержание |
| --- | --- |
| Идентификатор и заголовок | Постоянный тег транскрипции и понятное название |
| Источник | `автор` |
| Дата | Ровно то, что известно о получении текста |
| Тема | Предполагаемая тема без утверждения о проверенном переводе |
| Исходная транскрипция | Дословная запись автора из исходного файла |
| Текст для копирования | Отдельная версия с маленькими корректировками, если она отличается |
| Транскрипция с уточнениями | Пояснения к спорным звукам и вариантам чтения |
| Разбор | Наблюдения и аргументы без смешения с готовым переводом |
| Автоматическая расшифровка | Вывод модели с её названием и пометкой об экспериментальном статусе, если он есть |
| Толкование автора | Отдельная авторская версия смысла, если она предоставлена |
| Статус проверки | Что проверено по источнику и что остаётся гипотезой |

Поля «автоматическая расшифровка» и «толкование автора» не создают сами по себе подтверждённый перевод. Пустые поля опускаются. Для существующих материалов сборщик берёт опубликованный текст из Markdown и не меняет его ради шаблона.

Быстрая проверка актуальности: сборка записывает SHA-256 исходных файлов в `site/content-manifest.json` и в архив сайта. Для текстовых файлов перед вычислением хеша окончания строк приводятся к LF, чтобы Windows и Linux давали одинаковый результат. После отправки манифеста в GitHub и публикации архива выполните `python -B -X utf8 site/scripts/check_site_sync.py` из корня репозитория. Скрипт скачает только два небольших манифеста — из GitHub и с сайта — и перечислит различающиеся файлы; он не скачивает все HTML-страницы. Совпадение манифестов подтверждает соответствие опубликованной сборки исходникам на момент её создания, но не выявляет последующую ручную замену отдельных HTML-файлов без изменения манифеста.

При добавлении нового файла в `docs/transcriptions/` укажите в нём поле `Дата и время получения транскрипции: ДД.ММ.ГГГГ, ЧЧ:ММ` (время можно опустить, если оно неизвестно) и раздел `## Необработанная транскрипция` с дословным текстом. Для побайтно сохранённого авторского разбора генератор также понимает `**Дата:** 29 сентября 2026` и `## Исходная строка`; такая дата помечается датой разбора, а не установленным временем получения транскрипции. Из корня репозитория запустите `python -B -X utf8 site/scripts/update_calendar.py`: скрипт найдёт новые файлы, добавит записи в `public_html/data/entries.json` и запомнит обработанные пути в `calendar-index.json`. Он не изменяет исходные Markdown-файлы и останавливается с ошибкой, если не удаётся установить дату или исходную строку. Старые файлы без единого формата перечислены в индексе как уже учтённые; если нужно добавить один из них, передайте его путь скрипту явно.

При push новых файлов в `main` генератор календаря и сборщик страниц запускаются [GitHub Actions](../.github/workflows/calendar.yml). Автоматизация отправляет обновлённые JSON и манифест обратно в репозиторий. Для автоматической публикации на Tuqo нужен секрет репозитория `TUQO_API_KEY` с ключом проекта уровня `editor`; без него GitHub обновит исходники и манифест, но сайт останется на прежней версии. Никакие ключи в архив не включаются. Даты и известные часы сортируются по времени появления транскрипции; при неизвестном времени порядок записей внутри дня не утверждается.

Схема MySQL и скрипты импорта/публикации подготовлены, но текущий сайт не использует БД при открытии страниц. При отдельной настройке БД параметры доступа должны оставаться вне публичных файлов; обновлённый JSON-снимок публикуется на Tuqo только после проверки его содержимого. Проверка нагрузки для 100 одновременных посетителей ещё не проводилась.

Календарная дата хранится в БД как Unix timestamp в UTC для полуночи соответствующего дня по Москве. Такой timestamp служит ключом календарного дня и не обозначает время создания аудио.
