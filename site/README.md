# Сайт «Глоссалия»

Сайт показывает выбранные материалы [Glossolalia Explorer](https://github.com/hayOfLife/glossalia-explorer). Основной адрес — [glossalia-explorer.tuqo.ru](https://glossalia-explorer.tuqo.ru/). Исходная оболочка находится в `site/public_html/`, готовые для Tuqo статические страницы собираются в `site/build/`; записи для календаря находятся в `site/public_html/data/entries.json`.

## Структура

- `public_html/` — единственный каталог, который должен быть доступен посетителям.
- `public_html/data/entries.json` — опубликованный снимок записей для браузера.
- `calendar-index.json` — список уже учтённых файлов транскрипций; новые файлы сравниваются с ним.
- `scripts/update_calendar.py` — генератор календарных карточек из новых Markdown-файлов.
- `database/schema.sql` — схема MySQL 5.7.
- `database/seed.json` — начальные шесть записей, извлечённые из публичных карточек репозитория.
- `database/config.example.php` — образец параметров БД без учётных данных.
- `scripts/import.php` — однократный импорт начальных записей в пустую таблицу.
- `scripts/publish.php` — создание нового снимка из опубликованных записей БД.

## Оценки транскрипций

Tuqo раздаёт только статические файлы. Общие счётчики ведёт отдельный HTTPS API на VPS. Серверный процесс и его файл голосов отделены от публичных файлов сайта. Исходники API пока не отправлены в GitHub; эта страница описывает действующее размещение, а не инструкцию по его воспроизведению из текущего коммита.

Публичный API проверен тестовым голосом со снятием; после проверки счётчик вернулся к исходному значению. Для посетителей голосование появится после отдельной публикации подготовленных статических файлов на Tuqo. Никакие ключи или пароли в браузерный код и Git не добавляются.

Голос привязан к случайному идентификатору в браузере, а не к человеку: очистка хранилища или другой браузер позволяют проголосовать снова. На сервере сохраняется только SHA-256 этого идентификатора и выбор лайк/дизлайк. API ограничивает изменения голосов до 12 за 10 минут для идентификатора и 40 за 10 минут для IP; посетители за одним IP делят общий лимит. IP и счётчики лимитов хранятся только в памяти процесса и сбрасываются при его перезапуске. Эти ограничения замедляют накрутку, но не исключают её полностью.

Изменение от 30.09.2026 подготовлено в статической сборке: голосование есть у всех опубликованных транскрипций в календаре, заполненных раскрывающихся блоках и на отдельных страницах. Повторное отображение одного источника использует общий `reactionKey`; новости, страницы ситуаций без транскрипций, словарь и пустые блоки голосования не получают. Прежние ключи и накопленные голоса сохраняются.

Для локального просмотра и опубликованного сайта предусмотрены два экземпляра API. Браузер определяет локальную версию по `location.hostname`: `localhost`, `127.0.0.1` или `[::1]`. Она обращается к `https://94-232-41-163.sslip.io/glossaliae/reactions-local`, остальные адреса — к прежнему `https://94-232-41-163.sslip.io/glossaliae/reactions`. Режим нельзя переключить параметром страницы. CSP разрешает оба точных адреса API.

Боевой экземпляр по умолчанию работает в режиме `production` на порту 8791, принимает изменения только от `https://glossalia-explorer.tuqo.ru` и сохраняет прежний файл `/var/lib/glossaliae-reactions/reactions.json`. Служба [локального экземпляра](reactions-api/deploy/glossaliae-reactions-local.service) задаёт `REACTIONS_ENVIRONMENT=local`, порт 8792 и отдельный файл `/var/lib/glossaliae-reactions-local/reactions.json`; у неё отдельный системный пользователь. Локальный API разрешает только канонические HTTP/HTTPS Origin с тремя перечисленными адресами и корректным портом. Другие IP, поддомены `localhost`, `null` и запросы с боевого сайта не получают разрешения на изменение локальных голосов. Caddy передаёт запросы через [отдельный маршрут](reactions-api/deploy/Caddy-local-route.caddy), не открывая порт 8792 наружу.

Идентификатор браузера, сохранённый выбор и лимиты IP/ID разделены по средам. Локальная версия использует ключи `glossaliae-voter-id-local` и `glossaliae-votes-local`; боевые ключи остаются прежними. Одинаковая транскрипция и тот же браузер могут иметь разные оценки в двух средах. Очистка локального файла или исчерпание локального лимита не меняет боевые данные. Проверка Origin отделяет обычные запросы браузеров, но не является аутентификацией: самостоятельный HTTP-клиент может подставить заголовок Origin; прежние ограничения накрутки продолжают действовать отдельно в каждой среде.

Для добавления локальной среды к уже установленному API используется [сценарий](reactions-api/deploy/enable-local-environment.sh). Он требует временный каталог с проверенными файлами и SHA-256 действующего сервера и Caddyfile, проверяет сохранённое хранилище без записи и создаёт закрытые резервные копии конфигурации. При ошибке восстанавливает код и конфигурацию, сохраняя файлы голосов. У Caddy на этом VPS задано `admin off`, поэтому изменения применяются через restart службы. Оставшийся после остановленной установки локальный каталог можно использовать только с явным аргументом `resume-local-state` после проверки его расположения и содержимого.

30.09.2026 оба экземпляра включены на VPS. Их публичные HTTPS-адреса ответили `200` с отдельными разрешёнными Origin и списком из 33 ключей. В локальном браузере поставлен и снят тестовый лайк: локальный счётчик изменился `0 → 1 → 0`, а все боевые счётчики и SHA-256 боевого файла голосов остались прежними. Перекрёстные POST-запросы получили `403`. Обе службы оценок, Caddy и прежний Sheepfold relay остались активны. Проверки API прошли в Node.js на VPS: 17 тестов; статическая сборка прошла 25 локальных тестов. Для браузерных кнопок на Tuqo нужно вручную загрузить новый архив с обновлёнными JS и CSP; проверка боевой страницы после этой загрузки пока не выполнена.

Сборщик создаёт [список разрешённых транскрипций](reactions-api/transcriptions.json), который API читает при запуске. После добавления транскрипции и пересборки нужно отдельно обновить `server.mjs` и `transcriptions.json` на VPS и перезапустить API, затем опубликовать статический архив на Tuqo. Одного обновления архива недостаточно: ключи, отсутствующие в ответе старого API, остаются отключёнными. Сервер не принимает голос за ключ вне списка. Скрипт `deploy/install.sh` предназначен для первой установки и не запускается повторно для обновления.

Локальные проверки из корня репозитория в PowerShell при установленном Python и Node.js: после `python -B -X utf8 site/scripts/build_static.py` выполните `python -B -X utf8 site/tests/test_static_build.py`, `node --test site/reactions-api/server.test.mjs` и `node --check site/public_html/assets/site.js`. Первая команда обновляет сборку и список API; тесты проверяют общие ключи, размещение кнопок, сохранение старых голосов, запрет посторонних ключей и ограничения запросов. Сетевые запросы API-тестов направлены только к временному локальному серверу. Эти проверки не публикуют сайт и не подтверждают состояние VPS.

30.09.2026 браузерная проверка действующего сайта подтвердила отключённые кнопки; опубликованный HTML содержал `connect-src 'self'`, запрещающий запросы к внешнему API. Сборка разрешает только точный HTTPS-адрес API. Сервер на VPS обновлён до списка из 32 ключей; совместимость текущего хранилища проверена до установки, SHA-256 файла голосов до и после перезапуска совпал, все три серверные службы остались активны. Загрузка архива через панель Tuqo отклонена с сообщением о суточном лимите пяти деплоев. Повторного запроса через API не было; автор выбрал последующую ручную загрузку архива. Поэтому работа кнопок на опубликованной странице после исправления ещё не проверена.

## Локальный просмотр

Из корня репозитория в PowerShell при установленном Python запустите `python -B -X utf8 site/scripts/build_static.py`, затем `python -m http.server 8765 --directory site/build` и откройте `http://127.0.0.1:8765/`. Первая команда записывает готовые файлы в `site/build/` и `site/content-manifest.json`, не удаляя другие файлы; вторая показывает готовый сайт локально и не меняет файлы. Прямое открытие `index.html` как файла может заблокировать чтение JSON. Просмотр не проверяет доступность Tuqo либо API голосования.

## Обновление сайта и данные

Tuqo нужно обновлять отдельно от GitHub. Архив для загрузки создавайте из содержимого `site/build/`: в корне должны быть `index.html`, `assets/`, `data/`, `sitemap.xml`, `robots.txt`, `content-manifest.json` и каталоги отдельных страниц. Каталоги `database/`, `scripts/` и серверный PHP-код не загружаются как публичные файлы.

Сборщик создаёт отдельные HTML-адреса для основных разделов и всех опубликованных разборов, указанных в календаре или на страницах сайта. Внешний вид основных разделов берётся из той же оболочки и CSS. Ссылки разделов ведут по обычным путям; старые адреса с `#` не поддерживаются. `sitemap.xml`, `robots.txt`, уникальные заголовки, описания, canonical-адреса и разметка `CreativeWork` для разборов формируются при сборке. Разбор читается прямо из исходного Markdown без изменения файла. Источник транскрипции в карточке указан как «автор», а ссылка на Markdown позволяет сверить опубликованный текст с GitHub.

Обычный клик по «Подробно»/«Подробнее» или заголовку календарной транскрипции открывает полный разбор в окне поверх текущей страницы. Окно загружает текст с соответствующей статической HTML-страницы того же сайта; фон не прокручивается. «Закрыть» и Escape возвращают фокус к исходной ссылке и сохраняют место, выбранную дату и раскрытые блоки. Адреса отдельных страниц остаются доступными поисковикам и по ссылке «Открыть отдельной страницей»; клики с Ctrl, Cmd или Shift сохраняют обычное поведение браузера. При отсутствии поддержки `dialog` работает исходная ссылка.

Для новой карточки храните отдельно исходную транскрипцию и текст для копирования с маленькими корректировками, если он отличается. Сборщик берёт текст для копирования из поля `copyText` в `entries.json`, затем из раздела `## Текст для копирования` исходного Markdown либо из уже существующего блока `textarea` в оболочке сайта. Если отдельный текст не задан, он копирует раздел «Необработанная транскрипция» из исходного Markdown; для старых карточек без такого раздела берёт `bodyText` из календаря. Поле `bodyText` остаётся текстом календарной записи. Дату записывайте одним полем с известной информацией, не придумывая час. Тема, машинный разбор и авторское толкование должны быть различимы в исходном Markdown; отсутствующие сведения не заполняйте догадками. История правок карточки пока не ведётся.

Для новых материалов используйте такой порядок смысловых полей. Это шаблон для последующего наполнения, а не требование переписать уже присланные автором файлы:

| Поле | Содержание |
| --- | --- |
| Идентификатор и заголовок | Постоянный тег транскрипции и понятное название |
| Источник | `автор` |
| Дата | Ровно то, что известно о получении текста |
| Тема | Предполагаемая тема без утверждения о проверенном переводе |
| Исходная транскрипция | Дословная запись автора из исходного файла |
| Текст для копирования | Отдельная версия с маленькими корректировками, если она отличается |
| Транскрипция с уточнениями | Пояснения к спорным звукам и вариантам чтения |
| Разбор | Наблюдения и аргументы без смешения с готовым переводом |
| Автоматическая расшифровка | Вывод модели с её названием и пометкой об экспериментальном статусе, если он есть |
| Толкование автора | Отдельная авторская версия смысла, если она предоставлена |
| Статус проверки | Что проверено по источнику и что остаётся гипотезой |

Поля «автоматическая расшифровка» и «толкование автора» не создают сами по себе подтверждённый перевод. Пустые поля опускаются. Для существующих материалов сборщик берёт опубликованный текст из Markdown и не меняет его ради шаблона.

Быстрая проверка актуальности: сборка записывает SHA-256 исходных файлов в `site/content-manifest.json` и в архив сайта. Для текстовых файлов перед вычислением хеша окончания строк приводятся к LF, чтобы Windows и Linux давали одинаковый результат. После отправки манифеста в GitHub и публикации архива выполните `python -B -X utf8 site/scripts/check_site_sync.py` из корня репозитория. Скрипт скачает только два небольших манифеста — из GitHub и с сайта — и перечислит различающиеся файлы; он не скачивает все HTML-страницы. Совпадение манифестов подтверждает соответствие опубликованной сборки исходникам на момент её создания, но не выявляет последующую ручную замену отдельных HTML-файлов без изменения манифеста.

При добавлении нового файла в `docs/transcriptions/` укажите в нём поле `Дата и время получения транскрипции: ДД.ММ.ГГГГ, ЧЧ:ММ` (время можно опустить, если оно неизвестно) и раздел `## Необработанная транскрипция` с дословным текстом. Для побайтно сохранённого авторского разбора генератор также понимает `**Дата:** 29 сентября 2026` и `## Исходная строка`; такая дата помечается датой разбора, а не установленным временем получения транскрипции. Из корня репозитория запустите `python -B -X utf8 site/scripts/update_calendar.py`: скрипт найдёт новые файлы, добавит записи в `public_html/data/entries.json` и запомнит обработанные пути в `calendar-index.json`. Он не изменяет исходные Markdown-файлы и останавливается с ошибкой, если не удаётся установить дату или исходную строку. Старые файлы без единого формата перечислены в индексе как уже учтённые; если нужно добавить один из них, передайте его путь скрипту явно.

При push новых файлов в `main` генератор календаря и сборщик страниц запускаются [GitHub Actions](../.github/workflows/calendar.yml). Автоматизация отправляет обновлённые JSON и манифест обратно в репозиторий. Для автоматической публикации на Tuqo нужен секрет репозитория `TUQO_API_KEY` с ключом проекта уровня `editor`; без него GitHub обновит исходники и манифест, но сайт останется на прежней версии. Никакие ключи в архив не включаются. Даты и известные часы сортируются по времени появления транскрипции; при неизвестном времени порядок записей внутри дня не утверждается.

Схема MySQL и скрипты импорта/публикации подготовлены, но текущий сайт не использует БД при открытии страниц. При отдельной настройке БД параметры доступа должны оставаться вне публичных файлов; обновлённый JSON-снимок публикуется на Tuqo только после проверки его содержимого. Проверка нагрузки для 100 одновременных посетителей ещё не проводилась.

Календарная дата хранится в БД как Unix timestamp в UTC для полуночи соответствующего дня по Москве. Такой timestamp служит ключом календарного дня и не обозначает время создания аудио.

## Метка способа разбора

В начале файла разбора хранится служебная строка `разбор транскрипции: авто`, `разбор транскрипции: ручной, 100%` или назначенная автором процентная метка, например `разбор транскрипции: 95%`. На сайте она отображается справа под полем для копирования как «Разбор транскрипции: авто», «Разбор транскрипции: 100%» или указанный процент. Допустимы целые проценты от 0 до 100 без ведущего нуля. В календарных карточках метка находится под текстом транскрипции. Это обозначение способа разбора, а не оценка достоверности перевода.

Метка в файле имеет приоритет. Если её ещё нет, сборщик выбирает `manual` при наличии «пометки автора» или слова «уточнено» без учёта регистра, иначе `auto`. При интеграции нового разбора добавляйте соответствующую строку перед исходным текстом, сохраняя все байты исходного тела. Для `docs/transcriptions/T00027/part_8.md` автор явно назначил `manual`. Ранее записанные хеши присланных файлов относятся к исходному телу без служебной строки и пустой строки после неё.

Сборщик обновляет `data/analysis-modes.json`, поле `analysisMode` календарных записей и метки HTML-страниц из исходных файлов. Служебная строка в тексте разбора на сайте не показывается; после изменения метки выполните обычную пересборку сайта.

## Словарь на странице для ИИ

Таблица внизу страницы «для ИИ (for AI)» строится из [объединённого словаря](../docs/dictionary/combined.md). Каждый заголовок `##` задаёт слово или сочетание. Шесть столбцов — «Написание», «транскрипция», «Транскрипция получена», «перевод из словаря», «трактовка автора», «язык». Для явного заполнения полей используйте строки `**Написание:**`, `**Транскрипция:**`, `**Перевод из словаря:**`, `**Трактовка автора:**`, `**Язык:**`. Сборщик также читает существующие обозначения корня, ручной формы и авторского смысла; словарный глосс извлекает только из явно записанной пары леммы и значения. Пометки `, ZIPA`, `, W2V2` и `, Allosaurus` переносятся из отображаемой транскрипции в узкий столбец «Транскрипция получена»; если таких пометок нет, он содержит «ручная». Упоминания движков в тексте разбора на этот столбец не влияют. Столбец «язык» читает поля `**Язык:**` и `**Языки:**`, а при их отсутствии — явно названные языки в лексических сопоставлениях: непустые поля `**Иврит:**`, `**Японский:**`, `**Славянский:**`, пометки `лат.`, `греч.`, `арам.` и аналогичные, предложения о языке и поле `**Предполагаемый язык:**` с языковой группой исходной статьи. Несколько вариантов сохраняются вместе. Поле языковой группы для RUVI взято из ближайшего заголовка исходной таблицы; локальная языковая пометка имеет приоритет. Для точно совпавших B3-форм языковые пометки перенесены из столбца «Язык» итоговой таблицы исходного разбора со ссылкой на него; сокращённые и отличающиеся формы не сопоставляются автоматически. Алфавит, номера Стронга, URL и общие упоминания языков в ограничениях не определяют язык слова. Неизвестные поля показываются как «Пока не заполнено»; весь исходный текст остаётся под кнопкой «Разборы и источники». На телефоне шесть полей каждой строки располагаются друг под другом.

Совпадающие написания объединены; альтернативные значения сохранены отдельными подразделами. Присланный [исходный словарь](../docs/dictionary/slovar_kanala.md) сохранён дословно. Для следующих правок меняйте объединённый файл и пересобирайте сайт обычной командой: таблица включается в статическую HTML-страницу, а локальная оболочка загружает её из `data/dictionary.html`.

По указанию автора от 30.09.2026 при интеграции новых разборов добавляйте в объединённый словарь новые слова и явно уточнённые значения уже заведённых слов, со ссылкой на конкретный файл транскрипции. Прежние варианты и статус гипотезы сохраняются; неизвестные поля не дополняются догадками. Текст присланного разбора остаётся неизменным, кроме ранее разрешённой замены личного имени автора.
